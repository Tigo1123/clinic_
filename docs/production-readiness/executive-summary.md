# Executive summary

## Current status after remediation pass 2 — 22 October 2026

**Verdict remains A — NOT READY FOR PRODUCTION.** Pass 2 completed the 27-migration replay, a synthetic local query-plan review, a local restore drill, local least-privilege role checks, and the complete backend/frontend test suites. The backend passed 689/689 tests; frontend passed 50/50. The restored clone passed Prisma status/diff and app readiness. No production service was accessed.

No staging HTTP deployment existed: **0 VUs demonstrated**, 1000 not tested, deployed weak-network timings N/A, actual-edge TLS/HSTS/PHI cache policy unverified, provider DB grants/pooling unverified, provider RPO/RTO unknown. The local dump/restore took 247/605 ms, and app readiness after local restore took 951 ms; these are not provider recovery objectives. SessionStorage bearer tokens remain a High risk. See [Pass 2 evidence](remediation-pass-2.md), [load results](staging-load-results.md), and [restore results](restore-drill-results.md).

Pass 1 remediated the original optional-MFA policy, queue over-projection, unbounded query patterns, rate-limit architecture, dependency advisories and route chunking at source level. Pass 2 verified selected controls locally but did not validate provider deployment or edge behavior; residual gates remain in the risk register. The initial audit narrative below records the baseline and should not be read as current implementation status where Pass 1/2 update it.

**Verdict: A — NOT READY FOR PRODUCTION.** This is an evidence-based deployment gate, not a conclusion that the application is unusable. Several deployment-critical controls and capacity claims cannot currently be demonstrated: no staging/API benchmark, no completed concurrency test, no restore drill, and no verified hosting topology. The frontend has a sizeable initial payload, and the repository contains High npm advisories in both lockfiles (mostly build/dev tooling). Resolve the High findings and validate the actual production image before release.

The audit ran a Vite production build, measured unauthenticated public routes in Chromium using three throttled profiles, inspected backend/frontend/database/deployment source and ran `prisma validate`. It did not connect to Neon or Render, use real patient data, simulate authenticated workspaces, run a load test, or disrupt external services. Therefore no API p50/p95/p99, clinical-workflow result, or supportable concurrent-user ceiling is claimed.

Measured local production-build results at 390px: profile A (2 Mbps/750 Kbps, 100 ms, 4x CPU) public landing cold navigation 2.27s, LCP 1.85s, 36 requests, 663 KB transferred; patient login 2.02s/283 KB/30 requests; staff login 2.02s/336 KB/35 requests. Profile B (750/250 Kbps, 250 ms, 4x) patient login is usable by 4.52s; staff login became usable by 9.49s after a longer readiness capture. Profile C (300/100 Kbps, 500 ms, 6x) patient login is usable by 10.0s and staff login by 15.28s. These are local frontend-only upper bounds to observed controls, not production or API timings. See [browser results](weak-network-audit.md).

The most concrete capacity concern is unbounded aggregation in admin billing analytics: it loads all payments, refunds, doctor/appointment rows and dispensed prescription rows into Node memory. Unpaginated appointment queues and patient history endpoints also grow with data. Per-request auth performs a DB user lookup. The current Prisma pool and Neon runtime/pooler configuration were not verified; a separate direct PostgreSQL listener is used per backend process for token revocation. At 100 users pool/query pressure becomes a credible concern; 500 and 1000 are unproven and likely encounter DB connections, request fan-out, memory and event-loop contention before raw static serving.

Security strengths found include strict Zod request validation in many sensitive routes, Prisma parameterization, role checks, patient ownership enforcement, doctor queue isolation, short-lived JWTs with DB-checked auth versions, staff MFA support, Helmet/CSP controls and audit events on key security operations. Material gaps/risks include bearer tokens in `sessionStorage` (XSS token theft), optional rather than mandatory staff MFA, in-memory rate-limit state across replicas, excessive patient projection in appointment queues, development-only package advisories, and no demonstrated backup restore/least-privilege production DB role.

**Before first real patient:** fix/acceptably mitigate High dependency findings; verify production secrets/DB identities and TLS/edge headers; require MFA for privileged staff by policy; confirm production email/verification behavior; validate access with role-isolated tests; test backup restore; add alerting and incident ownership; run staged smoke/50/100 VU read-only tests and measure critical API paths. A controlled pilot can be reconsidered only after these gates pass. Redis/horizontal scaling is not a prerequisite for a single low-volume pilot, but multi-instance realtime and distributed rate limits need shared coordination before scaling.

See [top-ranked risks](risk-register.md) and [remediation order](remediation-roadmap.md). 1000-user concurrency has **not** been demonstrated.

5. **500 users (estimate):** pool/DB CPU, Node heap/event-loop and high-volume history/queue queries likely fail first; not measured.
6. **1000 users (estimate):** cannot safely estimate a supportable service level; current architecture has no evidence of capacity and would likely saturate DB/pool or Node before static frontend.

8. **Likely first endpoint failures:** billing analytics, pending/doctor queues, unbounded patient histories, login/auth bursts and slot availability/booking contention.
9. **DB connection strategy safe under load?** Unknown. A Prisma singleton is used; runtime pooler/limits are unverified and each backend process opens a direct PostgreSQL revocation listener.
10. **Hosting production-safe?** Not demonstrated. Root Compose exposes HTTP services and has no TLS edge/HA/central monitoring; a managed topology is required.
