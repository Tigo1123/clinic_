# Production readiness remediation pass 1

Date: 22 October 2026. This pass implements selected source-level remediations from the production audit. No production database was contacted, no production data was written, and no commit or push was made. Database integration tests and migration replay were not possible because an isolated PostgreSQL test database was not available.

## Outcomes

| Finding | Remediation and evidence | Status / residual risk |
|---|---|---|
| Staff MFA optional (PR-04, High) | Production configuration now requires `STAFF_MFA_POLICY=required`. Admin, doctor, reception, pharmacy and lab staff who authenticate without enrolled MFA receive a short-lived credential restricted to enrollment endpoints; it cannot authorize normal APIs or sockets. Successful enrollment requires a valid TOTP and returns one-time recovery codes. Existing MFA challenge/recovery-code flows remain; required policy blocks disable. Development/test remains optional by default. Unit/config tests cover policy and restricted behavior. | **Fixed in application policy; deployment gate remains.** Enroll every staff account before normal launch and test recovery on staging. There is no password-only fallback. If both authenticator and recovery codes are lost, use an identity-verified, audited off-band recovery procedure; there is no self-service bypass or admin MFA-disable endpoint under required policy. |

## Performance re-measurement

The Vite production build passed with 3,506 modules. Entry-chunk numbers above are reproducible from the build output. Weak-network runs used the localhost-only CDP harness, 390px viewport, cold browser cache, storage cleared, and profiles B (750/250 Kbps, 250ms, 4x CPU) and C (300/100 Kbps, 500ms, 6x CPU). An optional readiness-poll mode was added to the audit harness; it polls for visible, enabled input/button controls after load. It found 7 usable controls on each login screen and no failed requests. Cold first-usable time was patient B 4.68s, staff B 5.60s, patient C 10.20s and staff C 13.45s. Captured transfer through readiness was 265,666 B for each cold route in B and C. Warm repeat readiness was 1.70s/1.65s on B and 3.38s/3.33s on C; transfer 3.0/3.2 KB, respectively. Profile C patient reached 7 controls, so the fixed-wait fallback capture was premature rather than a permanent loading failure.

Original audit captures recorded profile B patient 296,424 B and 4.52s navigation; profile C patient 296,424 B and 10.00s; staff interactive by 9.49s / 15.28s respectively. Those are capture bounds and not an instrumented first-control timestamp, so treat comparisons as approximate. The new results show no meaningful patient readiness improvement; staff B/C improved in the new captures. Browser build output: entry JS 354.6 KB raw / 112.1 KB gzip, auth module 154.8 KB raw / 39.9 KB gzip, shared PasswordField 223.9 KB raw / 73.3 KB gzip. The largest emitted file remains AdminDashboard at 491.7 KB raw / 141.5 KB gzip but it is route-lazy. Full captures: `evidence/remediation-profile-b-readiness.json` and `evidence/remediation-profile-c-readiness.json`, alongside initial fixed-wait captures. No dashboard/API-backed routes were measured because no isolated staging backend and role accounts were available.

- Nginx syntax check passed using a temporary local config. It does not prove deployed edge headers/TLS.

## Staging plan before approval to deploy

1. Restore the current approved schema into isolated disposable PostgreSQL; use no production or Neon connection string. Apply the prepared migration there and test shared rate-limit atomicity, grants, cleanup, and restart behavior.
2. Start a staging backend with a least-privilege runtime role, a direct listener role, isolated mail/Google credentials, and metrics scraping. Serve the exact production frontend build behind a TLS staging edge with matching compression/cache/proxy rules.
3. Create disposable synthetic staff and patient identities only in that isolated environment. Run backend auth/authorization, queue projection, pagination, rate-limit and workflow tests; record cleanup SQL/script and delete synthetic identities afterward.
4. Repeat the browser B/C profiles with a readiness-polling harness and a stable production-equivalent server; record exact first-usable-control time, request totals and transfer bytes. Do not call a partial/lazy loading capture a success.
5. Run k6 smoke, then 50 and 100 VUs only after reviewing DB pool/CPU, Node heap/event loop, p95/p99, errors and rollback capacity. Increase later stages only after each explicit staging review. Do not target Neon production.
6. Perform a restore drill against a disposable clone, confirm the backup/PITR point and application recovery steps, then obtain separate production deployment approval.

## Verdict

The verdict remains **A — NOT READY FOR PRODUCTION**. Mandatory staff MFA and code-level minimization/bounds have improved, but production infrastructure/least-privilege verification, session-cookie architecture decision, reliable weak-network patient login, isolated DB migration/integration testing, staged load evidence, alerting and restore drill remain open launch gates. No 500- or 1000-user capacity is claimed.
